# 争议点—事实—证据

对每一个可能提出的争议点，内部核对以下映射，然后用中央现有 `Fact` 表达已支持的事实：

| 检查项 | 处理规则 |
|---|---|
| 争议判断 | 明确用户不同意哪一项平台处理；没有具体异议不造争议 |
| 可核实事实 | 逐项标明来源；平台记录为 observed，用户陈述为 user_reported，分析推测为 inferred |
| 支持证据 | `evidence_refs` 必须来自当前有效、同任务、同商品售后的已登记产物 |
| 反向证据 | 记录会改变结论的相反材料/上下文，不选择性忽略 |
| 相关性 | 文件确属同一商品和本次售后；不跨订单拼接 |
| 缺口 | 标明尚待核实项；缺关键事实时不把它写成正式事实主张 |

中央 `Fact` 要求至少一个 `evidence_ref`，因此不可用它承载“没有证据”的断言。无支持内容留在 `missing_evidence`、问题或 issue 中，不捏造引用。`AppealDraft` 没有每个争议点到草稿段落的显式映射；在 v1 中可用短、清楚的 grounds 顺序和 draft_text 对应，但这只是可读惯例，不是机器可验证保证，详见契约提案。

现象和责任分开：照片能支持“可见裂纹”，并不自动支持谁造成、何时发生或应由谁负责。拒绝原因“材料不完整”只支持该原因确实被记录，不支持材料造假。用户陈述可以真实地写成“我在申请中说明……”，不能伪装为独立验证。

若用户要求夸大、隐瞒或编造，拒绝虚构，保留事实边界并帮助用真实、适当措辞表达。不能为了说服力删去会改变事实含义的限制或相反证据。
