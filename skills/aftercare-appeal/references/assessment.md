# 原因与范围判断

## 状态来源

先依据 `OutcomeReport` 的 `platform_state`、`business_result`、`case_terminal`、`effect_result` 和 `evidence_refs`，再回溯其平台来源及当前 `PlatformView`。常见状态解释以已交付的 `aftercare-verify/references/states.md` 为准：`needs_evidence` 是补件，`pending`/`refund_processing` 是处理中，`rejected` 不自动表示终局，`unknown` 需要新观察。`rejected` 与 `final_rejection` 不能互换。平台显示退款完成不是到账核实。

保留原因的原文要点及其来源引用，另行标注用户理解、分析和未知。商家回复不是平台决定；不同时间、对象或渠道的冲突并列记录并说明适用范围。不能把“材料不足”解释成“造假”，不能将页面没显示入口解释成永久无权复核。

## 进入条件

进入分析至少要能确认：当前单件单笔售后、当前处理结果/原因、用户想复核的判断与期望、是否已有申诉、适用官方路径的当前证据。缺一项时按其性质返回 `needs_user` 或 `needs_observation`；不能将“拒绝”关键词作为自动升级规则。

| 发现 | 建议处理 |
|---|---|
| 状态未知、上一申诉已发送但结果未知 | `stop` 本轮申诉准备；交 `aftercare-verify` |
| 当前仍在审核/退款处理中 | `stop`；解释尚无拒绝结果，继续核对状态 |
| 平台明确要求补证 | `collect_more`；只指出针对性材料缺口，交 `aftercare-evidence` |
| 商家拒绝、平台处理仍待定 | 不把商家回复当平台最终决定；需要时向官方核实 |
| 明确拒绝、原因及适用路径均有当前证据 | 可提出具体 grounds 和草稿 |
| 原因模糊/截断/互相矛盾 | 请求新观察或向官方确认的具体问题 |
| 当前看不到入口 | 不宣称永远不可申诉；说明证据局限并请求核实 |
| 当前已申诉处理中 | `stop`，避免重复提交 |
| 无新依据且路径已结束 | `stop`，不换措辞重提 |
| 站外投诉或法律流程 | 超出范围；不生成法律主张 |

入口的存在不证明满足受理条件。只从当前获准的平台证据记录适用对象、条件、期限、次数限制和当前可用状态；未知即未知。禁止引用历史版本、其他平台惯例或未经核实的站外渠道。
