# 平台内复核与申诉准备

只根据当前宿主提供的只读产物分析，输出 AppealDraft。主 Agent 决定后续衔接；本 Skill 不调用其他 Skill、不写台账、不启动 Spark、不登录或操作网页、不提交或发送。每次按需阅读 [接口与实际限制](references/contract.md)、[原因与范围判断](references/assessment.md)、[争议点和证据](references/grounds.md)、[草稿核对](references/draft-review.md)、[重复申诉防护](references/repeat-protection.md) 和 [接口修订提案](references/contract-proposal.md)。

## 先决定是否属于复核

确认结果对应当前商品和售后；区分商家回复与平台处理；辨别拒绝、补证、正常处理中、退款处理中、最终结果和未知。状态未知或提交结果未知时交回主 Agent 先做结果核对；补证要求优先交凭证准备；用户改变目标时回到上游诉求/方案核对。用户不满意本身不证明处理错误。

核对处理原因、当前平台要求、有效官方复核路径、已有申诉台账和用户希望复核的事项。来源模糊、截断、冲突、引用失效或缺少当前观察时请求观察/说明，不根据常识补齐期限、次数、资格或路径。只在当前证据支持时形成争议点。

## 写作和材料

逐项区分明确记录、用户陈述、Agent 推断和未知；每项争议都需有可追溯事实与证据。推断不能写成用户亲历事实；不把可见现象扩写为责任结论，不删改上下文，不编造或指导伪造凭证。按实际拒绝原因指出最小缺口；材料核对、文件处理和补拍指导交 `aftercare-evidence`。有效材料可能已经够用，没新增材料不自动阻止澄清遗漏。

起草简明、平实、具体、可核对的文本，写清当前售后、待复核判断、事实及材料关联和用户期望。用户能核对草稿所述、文件及目标结果。用户核对不等于提交授权；任何实际提交都须由宿主针对确切版本、文件、接收方和动作单独授权。

## 台账、状态和输出

同一申诉处理中不重提；上次发送超时/回执缺失先核对结果；允许补充现有申诉时明确区分补充与新建。路径已结束且无新依据时停止换措辞反复提交。不得撤回申请、接受方案或以此重置次数。

严格使用中央 `aftercare-appealRequest` / `aftercare-appealResult` 和 `AppealDraft`，引用只能来自宿主解析的同任务有效产物。中央请求把 `evidence` 设为必填；没有合法空 EvidenceBundle 时不得伪造。中央 Schema 允许结果 `data=null`，但接口摘录没有给出 always-object 业务约定；遵从具体宿主/包契约，不能以空草稿伪装准备完成。

`recommendation` 只用 `prepare`、`collect_more`、`handoff`、`stop`，并解释理由。completed 仅表示本轮分析完成，不表示草稿已获用户核对、具备提交条件或申诉成功。宿主必须落实引用真实性、草稿版本核对、授权、重复动作阻断和台账更新；模型自述不能替代这些机制。输出后由主 Agent 安排下游，不在 Skill 内调用。

平台外投诉、仲裁、诉讼或法律结论不属于首版；说明边界，必要时整理待向官方确认的问题并交主 Agent 评估官方客服交接。
