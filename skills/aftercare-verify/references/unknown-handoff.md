# 未知与交接

提交后超时、断网、白屏、可能发出后的工具错误、缺回执、无成功提示和暂查无记录，不能直接失败。已知发送与未知业务效果并存时保留两者；先请求主 Agent 在许可范围查当前申请详情、列表或实际可用官方来源。只描述需要本商品/实例、动作之后、可比内容的证据，不编入口、轮询或重提。

需要新证据：needs_observation + issues；查证能力本身缺失、登录或权限受阻：blocked；分析已穷尽且无下一证据需求：completed + unknown，用户说明仍要清楚未知，宿主在途锁继续保留。没有新证据不反复刷新，不让 recover 绕过未知重提。retryable=false 不表示不能只读查证，只禁止把分析问题机械转成动作重试。

| 情况 | 主 Agent 可选择的交接 |
|---|---|
| 待审核/退款处理中 | 说明状态；宿主保存进度，用户回来再核对 |
| 平台补件 | aftercare-evidence，传实际要求证据 |
| 寄回/物流/预约后待取件 | aftercare-logistics；区分本人寄件和平台记录 |
| 拒绝且有复核路径 | aftercare-appeal，不提前终局 |
| 页面变化/查证受阻 | aftercare-recover，只读查证优先 |
| 无可行路径 | aftercare-handoff，未知发送仍保留 |
| 跨会话核对完成 | aftercare-resume，当前证据优先、旧授权不复用 |

以上是职责提示，不说明这些包已实现；由主 Agent 核查可用性后调度。本人需要补拍/实际寄件等才写 user_todos（Step四字段）；查页面、保存进度、登记结果是宿主待办，不让用户承担内部检查。v1 无 agent_todos 字段，用 issues 陈述缺口，不把文本当自动路由；候选协议提供结构化 observation_requests。

表达示例：
- “平台已经收到申请，目前显示待审核。现在还没有退款结果。”
- “刚才提交后页面超时，目前还不能确认是否成功。需要先查看申请记录，避免重复提交。”
- “平台显示退款完成，但还没有核实你是否收到款项。”
- “已经预约取件，尚未看到取件记录。请按已确认的预约安排准备包裹。”（只有确有预约安排才这样写。）
